# Design Handoff: Agentic Task Management Console

You are the design agent for an existing product. Backend V1 and V2 are built. Nothing on the frontend exists yet. Your job is to establish the **visual system and token layer**, not to write application logic. Your output will be handed to a coding agent that will implement it, so every decision must land as a named, machine-readable token or a written rule, never as vibes alone.

---

## 1. What the product is

An **agent-driven task manager** with a Linear/Jira-style task model, running on Cloudflare Workers + Durable Objects + D1, with Groq for inference.

Two interfaces sit on top of the same data:

1. A **deterministic task UI** (list/board + a task detail modal) backed by a REST API.
2. A **conversational agent** that manages tasks through natural language.

The agent is not a chatbot bolted onto a CRUD app. It runs a real agentic loop: it can call multiple tools in one turn, read the results, call more tools, and then answer. The UI has to make that loop legible.

### The full data vocabulary you get to design for

This is the entire task model. Do not invent fields.

```
id          string, server-generated
title       string
description string
status      todo | in_progress | done
priority    low | medium | high
due_date    date
created_at  timestamp
updated_at  timestamp
```

Three statuses. Three priorities. One date. That constraint is a gift: the semantic color layer should be small, exact, and highly legible rather than a generic 10-hue palette.

### The three agent tools whose activity must be visible in the UI

```
create_task
search_tasks    (structured filters: query, status, priority, due_before, due_after)
update_task     (id + changed fields)
```

---

## 2. Behaviors the design must actually accommodate

These are product requirements, not edge cases. Design for them explicitly.

- **Multi-step tool execution.** A single user message can produce: `search_tasks` → results → `update_task` → final response. The chat stream needs a way to render intermediate tool activity that is clearly subordinate to prose, not competing with it.
- **Task results rendered inside the conversation.** When the agent searches, it returns task records into the chat. These need to look like **authoritative data pulled from the database**, visually distinct from the agent's own prose.
- **Ordinal reference.** The user will say "mark the first one as done." Search results in the chat stream therefore need **visible, stable ordinals**.
- **Disambiguation.** When a request is ambiguous, the agent refuses to guess and asks the user to choose between candidates. This needs a real component: a prompt plus selectable options, in a state that reads as "blocked, awaiting your call," not as an error.
- **Cross-surface mutation.** The agent can change a task the user is currently looking at in the board or modal. Design an **update acknowledgment**: how a record signals it just changed underneath the user.
- **Persistent conversation.** History survives across requests and page loads. Design what a resumed session looks like on load, including a boundary between "earlier in this session" and "now."
- **Streaming.** Text arrives token by token and tool calls resolve asynchronously. Every state needs a pending form: pending message, running tool, resolved tool, failed tool.

### State/ownership distinction to express visually

The architecture keeps two things separate, and the UI should quietly reinforce it:

- **Agent state** (conversation, session, execution context) lives in a Durable Object. It is a transcript. It is ephemeral-feeling, chronological, narrative.
- **Task state** (the tasks themselves) lives in D1 and is the source of truth. It is a record. It is precise, tabular, referenceable, and should feel more "solid" than the conversation around it.

---

## 3. Surfaces in scope

Design tokens and component specs for:

1. **Application shell** — navigation, agent/session identity, global density. There is no auth, so no account menu, but leave a structural slot.
2. **Task index** — the deterministic list/board view. Must work at high row counts and read comfortably at a glance.
3. **Task detail modal** — view and edit all fields.
4. **Task create form** — same field set, server generates `id`, `created_at`, `updated_at`.
5. **Agent console** — the conversation surface: user messages, agent prose, tool invocation chips, tool result blocks, inline task cards, disambiguation prompts, streaming and error states.
6. **Empty / loading / error / offline states** for all of the above.

**Out of scope. Do not design these.** Task deletion, projects, labels, assignees, dependencies, recurring tasks, notifications, semantic search, authentication, workflow automation UI. They are deliberately deferred. Where you can cheaply leave an extensible slot in the layout or token naming, do so, and say where. Do not build the feature.

Known future work worth designing *around*: **Workflows** (durable scheduled automations, e.g. "remind me tomorrow", "every Monday create my planning tasks"). Expect an eventual fourth surface for scheduled/automated items. Reserve navigational and token space for a "scheduled/automation" concept without styling it now.

---

## 4. Aesthetic direction (locked)

**Minimalist covert-operations console.** Field terminal, not comic book. The reference point is a quiet, high-competence operations interface: dense information, ruthless hierarchy, nothing decorative that isn't also functional.

Commit hard to this. The single most memorable quality should be **restraint that reads as capability**.

### What that means concretely

- **Substrate:** dark-first. Avoid the default blue-black; consider a warm or neutral near-black with a slight temperature bias so it feels like a physical panel rather than a CSS default. Depth comes from **layered surface elevations and hairline rules**, not from drop shadows or glassmorphism.
- **Accent economy:** one high-chroma signal color, used sparingly enough that its appearance is meaningful. Everything else is achromatic. When the accent shows up, it should mean *something is live, targeted, or requires you*.
- **Typographic split:** a monospaced or technical face for **metadata** (task IDs, timestamps, status labels, tool names, filter arguments) against a refined text face for **prose** (agent messages, descriptions, titles). This split is the load-bearing idea. It is also how the eye separates "record" from "narrative."
- **Structural language:** hairline borders, corner ticks, register marks, alignment rails, uppercase micro-labels with wide tracking. Data should feel *plotted* onto the surface.
- **Motion:** precise and short. Register, sweep, reveal, lock. Nothing bouncy, nothing playful. Tool execution is the one place a sustained animation is justified, because something is genuinely happening over time. Respect `prefers-reduced-motion`.

### Hard bans

No neon cyberpunk clutter. No glowing purple or blue gradients. No fake radar sweeps, scanlines, Matrix rain, or ambient HUD noise. No glassmorphism. No emoji as UI iconography. No Inter, Roboto, Arial, system-ui stacks, or Space Grotesk. Nothing that would read as generic AI-generated dashboard output.

---

## 5. Primary deliverable: the token layer

Produce a **three-tier token system**. Tier boundaries must be strict: components consume semantic tokens, semantic tokens consume primitives, and no component ever references a primitive directly.

### Tier 1 — Primitives

Raw values with no meaning attached. Color ramps (each with enough steps to support both themes), a type scale, a spacing scale on a consistent base unit, radii, border widths, duration and easing values, and z-index steps. Name them by what they are, never by where they are used.

### Tier 2 — Semantic

Role-based aliases. At minimum, cover these roles. Name them however your system prefers, but every one of these needs a token:

- **Surfaces:** application background, raised panel, sunken well, overlay/scrim, modal.
- **Borders:** hairline default, emphasized, focus ring, divider.
- **Text:** primary, secondary, muted, inverted, on-accent, link.
- **Accent:** base, hover, active, subtle background, on-accent foreground.
- **Task status:** exactly three, `todo` / `in_progress` / `done`, each needing a foreground, a background, and a border treatment. `done` should recede; `in_progress` should be the only status that ever reads as live.
- **Task priority:** exactly three, `low` / `medium` / `high`. Priority and status must be **distinguishable without color alone** (shape, weight, position, or glyph), because they will frequently sit side by side on the same card.
- **Due date semantics:** overdue, due today, due soon, future, none. This is derived state, not a stored field, but it drives color.
- **Agent execution states:** idle, thinking, tool-running, tool-succeeded, tool-failed, awaiting-user-input (the disambiguation case), stream-complete.
- **Feedback:** success, warning, danger, info. Keep these distinct from status and priority tokens even where values repeat, so they can diverge later.

### Tier 3 — Component

Per-component tokens for: task card/row, status pill, priority indicator, due-date chip, chat message (user vs agent), tool invocation chip, tool result block, disambiguation prompt, modal, form field, button variants, and empty state.

### Output format

Deliver tokens as **CSS custom properties** in a single source file: `:root` for the default theme, `[data-theme="..."]` blocks for alternates. Provide a Tailwind v4 `@theme` mapping alongside it. The coding agent should be able to drop this in and start building without translating anything.

---

## 6. Theming requirements

- **`night` (default, dark).** The primary experience.
- **`day` (light).** Not an inversion. Re-derive it so the same hierarchy survives. In particular, the surface-elevation strategy that works on dark will not work on light; state the replacement rule.
- Structure the tokens so a **high-contrast** variant can be added later by overriding Tier 2 only. You do not need to produce it now, but prove the architecture supports it.
- **Accessibility floors:** WCAG AA (4.5:1) for body text, 3:1 for large text and for meaningful UI boundaries and focus rings. Every interactive element needs a visible focus state that survives both themes. Status and priority must be decodable by a colorblind user.

---

## 7. Also specify

- **Density.** Pick a default row height and information density for the task index, and state whether a compact mode exists. Dense is on-brand here, but only if the type scale supports it.
- **Type scale.** Actual sizes, line heights, weights, and letter-spacing for each role, including the tracking on micro-labels. Name specific font families and provide a fallback stack and loading strategy.
- **Grid and spacing.** Base unit, layout columns, container widths, and the standard gap rhythm.
- **Iconography.** Name a single icon library and a stroke/size rule. Do not mix sets.
- **Motion spec.** Durations and easing per interaction class: state change, entrance, exit, streaming text, tool execution. Include the reduced-motion fallback for each.
- **One or two representative mockups** so the coding agent has visual ground truth: the agent console mid-execution (tool running, prior results visible) and the task index. Static is fine.

---

## 8. Technical constraints

- The frontend targets **Cloudflare Pages**, consuming a Workers API. Assume a modern React + TypeScript + Tailwind v4 build. Prefer solutions that hold up under **streaming updates**.
- Everything must be reproducible in **CSS and code**. No raster assets, no background images, no textures that require a file. If you want grain or depth, it has to be expressible in CSS.
- Component structure should be compatible with a headless primitive library for behavior (dialog, popover, listbox). Style through tokens, not overrides.
- Keep the font count low. Two families, three at absolute most.

---

## 9. Acceptance criteria

Your handoff is complete when a coding agent can, without asking a follow-up question:

1. Copy one CSS file and have the whole token layer available in both themes.
2. Build a task card, status pill, priority indicator, and due-date chip using only named semantic tokens.
3. Render every agent execution state, including tool-running and awaiting-user-input, with defined tokens and motion.
4. Know exactly which fonts to load and how.
5. Know which decisions were deliberate and which are open, because you listed them.

Close with a short **open questions** section for anything you deliberately left for a human to decide.

---

**Yours:** every specific value. Palette, hues, exact fonts, scale ratios, radii, density, motion curves, component anatomy, and how far to push the operations-console language before it becomes costume.
